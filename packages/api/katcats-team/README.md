## Summary

This private development package adds persistent members, logical Bot groups and direct member group chats to the existing Katcat shell. ## Configuration and ownership

The main Bot tile can collapse into one compact row while retaining its conversation and headquarters actions. Its browser-local preference survives reloads independently of group folds and member records; an older preference starts expanded. Narrow sidebars retain their existing avatar controls.

`workspaceRoot` is required and absolute. Each member receives a directory at `workspaceRoot/bots/<BotId>`; directory links are rejected before creation. `mainName`, `mainRole`, `ordinaryGroupName` and `chatGroupName` configure first-use labels. Moving a member between logical groups changes neither files nor Session identity.

Each private Session belongs to a DSH filesystem Workspace registered for that member's assigned directory. This registration enables the existing conversation and composer; it is independent of logical Bot groups. New members are published only after registration and Session attachment succeed. Startup repairs missing registrations or membership for existing members using their assigned directories, without replacing their Session IDs, moving files, or rewriting conversation history. Workspace identities remain in the existing DSH registry rather than adding fields to the member record.

The Host owns `ctx.katcatsTeam`; its generated Remote namespace is `katcatsTeam`. Owner-only commands read and follow snapshots, create members and groups, edit member identity and appearance, and rename, reorder or delete custom groups. Bot and group-chat entries share custom groups. Deleting a custom group first moves its chats to the system chat section in one group-directory write, then moves its Bots to Ungrouped and removes the section in one team-directory write. Interrupted or rejected writes preserve valid references and can be retried; the section remains if the second write fails. Bot and chat identities, Sessions and working files remain unchanged. The main member and the two system groups remain present. Quick creation needs only a name and optionally an approved avatar, and starts a general assistant without a model request.

The main Bot defaults to “小兢会计”. With the default configuration, startup renames a saved main Bot named “Katcats” through the existing pending-rename transaction, updating its Session title while retaining its identity, conversation history and working files. Custom main Bot names and ordinary members named “Katcats” remain unchanged.

New members follow DSH's current base model, without requiring credentials or catalog availability during creation. The prompt-admission hook resolves that policy before image validation; the resulting selection uses the [Session-only selection API](../session-controller/README.md) and never saves the application default or changes another Bot. Fixed choices retain their normalized override. Existing `follow-global` records now follow later base changes without rewriting member records. Owned group dispatch and continuation also resolve this policy; unrelated direct SDK, ACP or scheduled followups are outside this admission hook.

Member settings read the shared [model directory](../../client/ui-model-selection/README.md). Candidate models saved in Settings → Models become choices for every Bot without a restart; ChatGPT candidates require successful connection tests before saving. Model changes remain drafts until Save succeeds and then apply to new messages for that member, without changing other Bots or the application default. Settings distinguish the saved route from the last recorded request model; a queued selection does not count as an actual request. Credential and provider updates refresh the shared catalog, a Host replacement clears its old choices, and late responses cannot overwrite newer choices or publish after disposal.

The Client replaces the workspace-list slot and registers a workspace category whose activation opens the same creation dialog. It retains the existing conversation, composer and right-sidebar tools; member settings occupy an additional tab. Explicit member navigation and newly created Bot or group conversations reveal settings from the matching composer's committed view, after the public sidebar surface is available, including blank conversations. Navigation and settings failures are reported separately. Ordinary members choose from ten supplied Bean Bot silhouettes. Their transparent PNG masks preserve independently selected colors. Existing shape IDs stay valid; choosing an icon does not change the Bot’s saved responsibilities. The main Bot uses the supplied Xiaojing portrait independently of its saved shape and color; its settings do not offer the ordinary appearance picker. Working directories are currently read-only in settings.

Each application open selects the existing main Bot conversation with its right sidebar collapsed, including first use, teams with no ordinary Bots and a saved expanded sidebar. Startup waits for both product directories and an addressable main Session; a catalog refresh or native saved selection cannot consume that choice early. Explicit Bot or group navigation supersedes the pending startup choice and remains selected across later directory updates and reconnection. Manually opening settings cancels a pending startup collapse. Startup does not create a separate general Agent conversation or clear the main Bot's history. Blank main and ordinary Bot conversations show the supplied team artwork and the same localized finance-team title above the composer: “小兢会计，您的AI财务团队” in Chinese and “Xiaojing Accounting, your AI finance team.” in English.

The sidebar shows the supplied main-Bot portrait in a larger unframed tile, and the same portrait appears in its conversation header and settings. Saved ordinary shape IDs and colors remain valid; an ordinary group manager retains its selected Bean Bot avatar and separate diamond marker. The create-group control appears above custom groups, followed by group chats and Ungrouped; each section folds independently. Without a saved entry order, default Bot creation places the new entry first in Ungrouped; explicit group choices remain honored. New custom groups precede older groups; new chats precede older chats when no entry order is saved, while pins retain priority. Section totals appear in parentheses immediately after their names. Each section counts its Bot and chat entries, with every chat counting as one unit; each chat row shows its saved member count. Each custom group's menu moves it up or down within the saved custom-group order, or opens a deletion confirmation; boundary moves are disabled and system sections stay fixed. Order uses the existing group array and survives restart. Bot and chat entries share pin, move, rename, copy-ID and delete menus, available by their action button or context menu. Moving either entry changes only its logical group; its type's system section is always an available destination. Renaming uses a name-only dialog; deletion requires confirmation and accepts only acknowledged Host results. The list scrolls without a scrollbar and offers a button when more items remain below. New Bot and chat selections unfold their section and scroll only this list to center the selected row within the available scroll range. The Katcats product composition labels the primary action Create new Bot, folds global tools by default, and places usage below them.

Bot and group-chat rows can be dragged before or after another row in the same section. The actual row follows the mouse or pen while nearby rows slide aside; release saves the destination. Pinned and unpinned entries remain separate, and the main Bot stays fixed. Escape or an interrupted pointer gesture cancels the preview; touch gestures retain normal scrolling, and reduced-motion settings disable the sibling animation. The browser-local sidebar preferences save the mixed entry order across reloads and restarts without changing membership or Session records. New entries follow saved entries in their pinned or unpinned section; removed and departed entries are ignored. Cancelling a drag or dropping outside its section leaves the order unchanged.

Deleting a Bot requires an idle private Session, no current group membership and no active automation or other reported Session activity. Deleting a group stops its owned work before removing its directory entry and dispatch journal; active automation must be stopped first. Both operations archive exact owned Sessions in the existing Workspace registry while retaining their history and working files. Failed directory writes roll back only the archive changes created by that deletion; an incomplete rollback is reported explicitly rather than claiming success. Retained memories and schedule records are not deleted.

Bot and group settings start at the existing minimum width and retain manual widths per settings provider for the current run. Bot, group and global settings use bold section headings. Forms scroll without a visible scrollbar; the group roster is collapsible. Dedicated main, ordinary Bot and group input hints use locale-owned copy and do not replace actionable blocked, unavailable, queued or plan-mode hints. Their composers hide workspace, preset, model and permission controls while keeping the original editor, attachments and sending. Model selection remains in Bot settings. Permissions use the original selector and risk confirmation in the settings panel: a Bot targets its private Session, and each group member row targets only that member's execution Session in this group. Neither changes the global default. Hidden panels, unavailable members and disconnections release group references; connection resets reopen both directory streams, keeping retained directories loading until fresh snapshots arrive. Missing group bindings never fall back to the transcript or private Sessions.

Group settings separate basic information, the finance connection, task records, members, group roles, collaboration, permissions and work resources into independently collapsible sections. Collapsing a section preserves unsaved form values. The ledger card uses the last observed access result to distinguish a reachable connection from a historical verification or failure.

Bot settings use the avatar labels’ weight for field headings. A Bot’s instructions and each saved group member’s responsibilities show up to eight lines in a read-only field. An arrow expands longer text in place and collapses it again. Select the pencil to edit the full text in a white field, then save beside the heading. This saves only that responsibility and retains other settings drafts. Clearing a group override restores the Bot’s own instructions.

Group settings keep Basic information visible. Other sections start collapsed. The arrow below Basic information expands them together when all are closed and collapses them when any is open. The member list shows the current selection for the group. Its plus button lists eligible Bots outside that selection. Save settings to apply membership changes. Finance connection cards in Bot and group settings start collapsed and show their status in the heading.

Group settings also offer one preset for all saved ordinary members, with one shared risk confirmation and individual rows retained. All exact group execution Sessions, permission projections and command access must be ready before selection. Unsaved settings, saving, hidden panels, unsupported legacy members and disconnections disable the batch. Members update sequentially through the public permission command; individual rows are locked during the batch. A changed roster or connection invalidates confirmation. Cancellation or an unconfirmed command stops remaining dispatch and reports each member as applied, not run, command unavailable or unconfirmed. Applied changes are not rolled back, and unconfirmed outcomes require checking the member's permissions. Private chats, other groups and global defaults remain unchanged. Automatic approval is unavailable when any target uses the finance preset.

The selected group manager and a shared member permission preset use white text on black in both themes. An unassigned manager or mixed member permissions retain the neutral selector style.

Owner messages in group chats and private conversations with the main or ordinary Bots use black bubbles with white text in light mode and white bubbles with black text in dark mode. User bubbles retain the shared standard radius and padding without a visible inset border. Avatar palette colors remain independent.

Bot, chat and custom sidebar-group menus open at the pointer; action buttons retain their anchored menus. Copy success and clipboard failures appear in the application notification area. Settings menus follow the host theme; dispatch-room menus retain their orange accent.

## Conversational members

The main Bot inspects the member roster, creates members with lasting roles and changes member avatars. When the group service is composed, it can create requested group chats from saved ordinary members and appoint a selected member as manager. It remains outside group execution. Each member can save only its own private role; tool discovery and execution both enforce the exact live Agent and its membership. Role text does not grant tools, change permissions, switch models or alter working directories. Quick creation remains a general assistant, and one-off work does not implicitly change its saved role.

Conversational creation uses the same serialized member operation as the menu, with the role and selected avatar included in the first durable creation intent. Results report the committed member rather than a proposed identity. Each saved Bot becomes the selected blank conversation; a subsequently created group chat becomes the selected group conversation. Settings retain explicit drafts and save only edited fields, so saving an appearance change does not overwrite a role saved by a conversation tool. Web uses the existing generic tool cards for actual arguments and results.

The main-only `create_bot` accepts an optional `avatar` with one of ten Bean Bot `shape` values and one of the eight picker colors; omission preserves `classic` and `#FF2849`. `create_bots` accepts the complete requested batch with names, roles and optional avatars. Only that batch counts toward the color limit: its first eight members use distinct preset colors, repeated or omitted colors receive unused presets, and only additional members can use other six-digit colors. Existing Bots never consume batch colors. All inputs are validated before creation; a later storage or Session failure stops the batch without rolling back saved members. Inspect `list_bots` before creating only missing members. The main-only `set_bot_appearance` changes an existing member's requested avatar without changing its role, model, group, Session or working directory; it is not an alternative creation path. Results include the actual saved avatar.

After all requested members are confirmed, `create_group_chat` saves their group and optional manager through the same durable directory as manual creation. The sidebar receives the saved group. The main Bot asks where to place new Bots or a team when the request leaves the location open. It can use an existing folder or call `create_bot_folder` for a new named folder, then pass the same folder ID for the new members and chat. Concurrent identical creations reuse the saved group, including the folder when specified. `list_group_chats` recovers pending creation and returns group metadata without transcripts. On failure or cancellation, inspect it before retrying or claiming the group is ready.

`list_bots` labels the built-in default Bot group `未分组`, without renaming persisted groups or user-defined labels. Writing a color in role text does not apply an avatar change; the main Bot confirms appearance from the saved result.

Cancellation is checked before mutation admission. Once a durable intent has been accepted, the operation finishes consistency work even if the caller cancels. A cancelled, interrupted or failed result can therefore coexist with a saved member or appearance change. Tool guidance requires the main Bot to inspect the roster before retrying, without automatically repeating the change. Recovery reuses a matching unfinished intent; a new call after completed creation is a new operation, without an exactly-once guarantee.

## Group conversations

In group settings, the Task records section uses white text on black and a white Task details button with black text. Its header counts all registered tasks in gray, completed tasks in SUDO green, deliveries awaiting acceptance in orange, and blocked tasks in red, with white numerals in compact badges that expand for additional digits. Counts follow saved task states even while the section is collapsed. The archive dialog follows the host's light or dark theme with SUDO green accents. Archives opened from either dispatch view use a fixed dark background with orange-gold accents.

Group settings and both dispatch views open the same task archive. It follows saved group updates, labels disconnected data as stale, and marks the current task by its saved run input. Handoff lists follow new records by default. Scrolling up or jumping to the top pauses only that list, and Jump to bottom restores following.

The owner can select an open or blocked record and continue that exact task. A matching paused run resumes where it stopped. An idle group sends a new instruction to the saved responsible member and retains the task's goal, criteria and next step. Continuation is unavailable for unknown outcomes, removed owners, incompatible ledgers and unconfirmed legacy records in a bound group. Finish or stop a saved run before switching the group's ledger.

New owner inputs retain `coordinationVersion: 1`. `record_group_task` records a business goal, owner, acceptance criteria, stage, next step, artifact references and exact owner-message identities. A direct recipient can explicitly continue its existing task across runs; delegated members inherit the association and cannot reclassify it. `plan_group_work` creates an open record for an unclassified direct request, with unspecified acceptance criteria until recorded explicitly. `find_group_tasks` searches tasks on the current group ledger and bounds results by `historyPageSize`.

The responsible member submits a finished result with `record_group_task` and `submit_delivery: true`, using the saved nonempty acceptance criteria. After required review, file registration and successful receipt publication, ordinary tasks complete with `completionKind: criteria`; they do not wait for an owner acknowledgement or prevent further work. Only `human_review_required: true` leaves the result awaiting human review and opens its confirmation dialog. Dismissing it keeps that result pending without blocking unrelated tasks. Intermediate decisions use the group question flow. Odoo writes, including posting, require operation approval before execution; a completed, verified operation does not by itself require another acceptance dialog.

The owner can confirm a delivery in the review dialog or task archive, or send a standalone acceptance in the group chat. Confirming in the dialog or archive saves the accepted revision without requiring a separate chat message. An explicit confirmation completes the sole eligible delivery in an idle group on the current ledger. If the group is still working or has multiple eligible deliveries, the owner selects the exact revision in a dialog. A standalone “可以了” applies only immediately after an eligible delivery in an idle group. It prompts for confirmation when that delivery requires human review. The original chat message and selected task are saved together, without starting a member turn.

Other clear acceptance wording is interpreted by the current responsible member through `accept_group_task`, without an additional classifier model. The tool requires the complete original owner message, an earlier published result, its exact task revision and the current ledger. It records `completionKind: owner` atomically with the input. Assistant self-claims, delegated messages, later results and other ledgers cannot supply acceptance. Unclear intent, mixed requests and ambiguous targets need clarification or manual archive acceptance; model interpretation is not guaranteed to be infallible.

When a task owner leaves the group, the current manager can record an explicitly authorized takeover of open or blocked work on the same ledger. `record_group_task` requires `take_over_owner: true` and the complete original `owner_transfer_quote`, preserving the goal, nonempty criteria and existing evidence. Takeover and delivery are separate actions; no owner is silently reassigned.

Automatically appended context excludes bodies explicitly assigned to other business tasks. Unclassified messages remain shared, preserving corrections and common constraints. Current input and permitted ancestry remain complete; `read_group_history` retains deliberate access to permitted originals. Classification is model-driven and may require clarification. Existing member Session history is not erased or split into separate task Sessions; these changes reduce new unrelated injection rather than guarantee context isolation or a token-saving percentage.

A confirmed blocker creates a durable, one-shot explanation obligation for an eligible task owner or group manager. A waiting caller's saved response or blocker report fulfills it; otherwise the group driver starts an explanation after existing work settles. It does not repeat the failed operation or bypass independent review. Restart retains the obligation but waits for explicit continuation. Unknown outcomes still require inspection, Stop cancels pending obligations, and an incomplete follow-up pauses visibly instead of looping.

The group header opens an on-demand dispatch room titled with the saved group name. Its HQ scene displays real member identities and recorded task handoffs, with a separate accessible member and task list; it has no department-progress strip, synthetic tasks, progress percentages or token estimates. Closing the room releases the iframe and its renderer. The entry owns room styles and passes class names into the lazy scene, keeping startup independent of shared stylesheet chunks. The scene is adapted from the licensed HQ artwork; its required notice remains visible and its license is retained in `artwork/hq/LICENSE`.

Live mode reads the group directory, task lifecycle journal, public replies and existing pending-question/approval status. Replay advances a local root-Session sequence cursor without prompting models, running tools or changing task state. Earlier history loads on request; missing or recovered history remains labeled. Recorded participant identities supplement the current roster, without reconstructing unrecorded membership changes. Public review comments remain replies, not machine-confirmed review approval; answering questions, approving operations and opening registered deliverables use the original group chat. Global dispatch rooms are outside this view.

The live execution panel retains only the selected group’s executor Sessions and shows the latest 100 loaded execution events, including steps, tool requests, nested tool execution and outcomes. Replies, reasoning, arguments and result bodies do not enter this log. Each row places execution status before member identity and time; overflowing status text scrolls horizontally, pauses on hover and respects reduced motion. Scrolling upward suspends following; the handoff list has a jump-to-bottom action. Closing the panel, switching to replay or disposing the plugin releases read subscriptions without stopping work. Reconnect reacquires executor references; unavailable records remain visibly unavailable. Replay hides live execution activity. These views make no model requests.

The scene uses native HQ glowing arcs for recorded handoffs, with moving particles only on active links. Other directory Bots appear as labeled visitors in live mode and walk public corridors with identity labels hidden until the pointer is over the visitor; moving away hides the label again. Visitors do not join tasks or acquire group execution Sessions; replay omits these ambient visitors. Transparent text overlays preserve the native HQ typography and colors. The top-right control cycles overview, tour and top-down cameras; personal camera controls follow real identities. Escape closes the room even when the scene has keyboard focus, without stopping tasks. The bottom task-progress line counts recorded dispatch states for the displayed run without inferring overall completion. People shows a compact, searchable roster with manager/member filters, one-line responsibilities, saved model routing, current group-executor permissions and live state. Details expand the full role, provider, reasoning effort and group working folder. Permission reads never use private Bot Sessions; unavailable or disconnected reads are labeled unavailable, including while viewing replay. The compact activity feed stays fixed above the independently scrolling handoff list. Handoffs start collapsed with sender, recipient, task summary and state; their details retain instructions and replies. The bottom member strip is omitted. Hovering or focusing a scene name shows the Bot’s full role, group position and state; clicking a member filters handoffs. Run duration appears beneath the compact group heading, separate from Token metrics. Dragging the heading moves only the room overlay, with native window dragging disabled for the dialog.

Group usage sums settled assistant-attempt records attributed to the selected run by delivered group input, deduplicating turn/step/retry samples. The panel reuses reported input, cache and output buckets without adding reasoning again. Missing usage, unloaded history or unattributed attempts remain labeled; no private or visitor Session is read. Calls count returned attempts, and auxiliary calls such as separate summaries are excluded. Fees are hidden because the account ledger has no group attribution.

The dispatch-node icon beside the main Bot badge opens a separate global headquarters component, with a Headquarters tooltip. In the collapsed sidebar it remains below the main avatar. The avatar and name still open the main Bot conversation. Its central office belongs to the directory's `mainBotId`; each group occupies one furnished room with its saved manager at the rear desk and members at individual desks. Larger rosters add desk rows with scaled furniture. Rooms retain their addresses during the window lifetime and use floors of eight rooms. Shared Bots have separate group appearances and execution states; independent Bots appear in the common area. Selecting a room or group strip subscribes only to that group's executor activity and usage, releasing the preceding subscription first. The fixed activity feed and independently scrolling handoff list show the selected group's current receipts; full history and replay remain in the standalone group dispatch room. Missing data stays unavailable, and closing either view does not cancel work. Both dispatch dialogs fit within the shared modal safe area on opening, leaving native window controls unobstructed. Task records use a compact header, prominent counts and separately scrolling task/detail panes. Status markers show the saved business state.

Headquarters signs connect directly to the rear wall cap with a short stem for the back row and outside the left or right walls for side rooms, independently of member labels. Member labels share the hover frame, show status in color, and expand duties on hover. The fullscreen control preserves the selected group and camera; Escape leaves fullscreen before closing the headquarters. The overview counts distinct executing Bots across group and private Sessions and groups with live processing activity; disconnected counts are unavailable. Its clock follows device-local time. Personnel lists all created Bots by group, plus the main and ungrouped Bots; shared identities count once in the total. Permissions appear only for the observed group's ready executor records. Bottom completion is completed dispatches divided by recorded dispatches in the current run, or latest retained run when idle; explicit non-participation is excluded. Failed or unknown outcomes never count as completed, empty runs have no percentage, and new dispatches can lower the ratio. This measures recorded dispatch completion, not business acceptance.

The separate `/chats` Host entry provides `ctx.katcatsChats` and the `katcatsChats` Remote namespace. It requires the same absolute `workspaceRoot`; `relayLimit` defaults to 16 task starts across all group members per round. Existing groups retain their saved limit. Each group uses `workspaceRoot/chats/<ChatId>`. New groups contain only explicitly selected ordinary Bots, with at least one member and an optional responsible member. The creator Bot is not inserted. The owner can select, change or clear the responsible member in group settings. Manual creation keeps the dialog within the available window height, scrolls its fields when needed and keeps Cancel and Create visible.

The group root Session is a transcript container and never makes a model request. The original composer uses an exact-Session transport registration to admit owner messages and stop group work. Its private, internal and unrelated Session routes remain unchanged. Each ordinary member has another Session for that group; two groups and a private conversation never share that member's Session. Group Sessions share the group's working directory. Their prompts use group-local responsibility overrides or saved member roles and public group context, without copying private-chat history. Internal execution Sessions do not become extra team-sidebar members.

Explicit member mentions select only those members, in saved roster order. An unmentioned owner message goes only to the current ordinary manager, or the first ordinary member when no eligible manager exists; this fallback does not save a new manager. Initial recipients and `collaborationVersion: 1` are committed with accepted input and stay fixed across retries and restarts. Previously accepted inputs without that version retain their saved recipients and legacy execution rules. A successful pass ends an irrelevant turn without creating a chat bubble. A member request waits for its recipient's actual completed reply or confirmed pass, returning the saved outcome and reply identity after publication. Busy targets are refused instead of creating circular waits. Replies do not start another broadcast round. Dispatch uses the member's current model policy only in its group execution Session.

Each executor receives previously unseen public messages by identity, retaining distinct messages with equal text. Current owner content, attachments and handoff instructions are included once; confirmed results remain available before transcript publication. A versioned context manifest is persisted with admitted member input, so preparation and queueing do not acknowledge receipt. With no retained manifest, `initialHistoryMessages` supplies the latest 20 permitted public messages plus the current task. Normal Session compaction retains summary memory and delivery identities; trimmed or replaced history is recalculated from retained events. `read_group_history` retrieves original messages by identity, keyword or cursor within this task's permitted group history. Private conversations, other groups and later owner tasks remain inaccessible. `historyPageSize` defaults to 20 items and `historyPageMaxChars` to 16000 text characters; partial results provide a continuation cursor. Historical numbers, decisions and evidence require consulting originals rather than treating a summary as proof.

The user can assign a responsible member and group-specific responsibilities in conversation. A currently executing member's scoped role tool saves the requested group settings before acknowledging them. Changes preserve private Bot identities, other groups, permission grants and historical sender snapshots. The group editor starts from each member’s current effective role, so the owner can append to it or revise it directly. Untouched members keep their saved or inherited roles. Private Bot settings can edit the saved default independently.

Every member prompt includes the roster, identities and effective group responsibilities. For versioned work, `plan_group_work` records the member's task, optional colleague assignments and review reason; an empty assignment list permits individual work. Members may use `ask_user_question` to clarify requirements before recording that plan; business operations still require it. Financial conclusions, data changes and explicitly requested reviews require a different current member. Models classify the task; runtime enforcement applies to the recorded policy, not to an infallible semantic classifier. Reading, calculating and preparing drafts are allowed before collaborators finish. Declared work still needs actual results before final delivery. Separate requests dispatch colleagues; no additional coordinator model is inserted. Public handoff instructions remain original group data, never private conversation imports or assistant speech.

`request_group_member` can bind candidate text and existing files to one parent delivery and one review child. The Host captures exact content versions through the configured `fs` provider; `reviewCandidateMaxBytes` defaults to 8388608 cumulative bytes across text and files, rejecting excess without truncation. Only that review child can call `submit_group_review`. A completed, persisted approval for the same candidate permits final delivery; ordinary replies, self-review, unknown outcomes and other versions do not. File contents are checked again at presentation and completion. The group publishes the exact approved text from the saved candidate. The member registers every approved file with `present` before finishing, and the registered file set must match the reviewed candidate. Files-only delivery displays the registered files. Changes to the candidate require another review. Normal execution and restart recovery use the same completion checks. After at most one correction, a known incomplete review retains the draft and marks the current task pending review while the group accepts further messages. An unconfirmed review record still requires inspection before continuing. Existing permissions and external-write approvals still apply; review adds no transaction rollback.

Business assignments require the corresponding persisted non-review child result; a review reply does not also finish that member's business assignment. Candidates can name their saved source deliveries, excluding those preparers from review. For declared data changes, an Odoo candidate captures the bound target, model, method and normalized parameters. The runtime checks approval of that exact version before operation approval and again at actual dispatch. The resulting records require read-back and a separately reviewed final result; approval to perform a write is not evidence of its outcome.

One owned driver orders each group's initial member opportunities. Delegation tools remain exclusive and execute in order: a delegated member runs in its own idle executor while the calling member awaits its result, and one executor never accepts two running tasks. After a delegation, other tools from the caller's same model step are refused until a new step can read the real result. After the current member and its awaited dependencies finish, a queued owner input takes priority over old automatic handoffs and receives a fresh budgeted run; later inputs retain their order and stable message and request identities. A durable receipt retains the sender's name and avatar snapshot. The member Session is flushed before that receipt commits, and the reply is appended and flushed into the transcript without waking a root Agent. Stable input and reply identities prevent duplicate publication after retries. The Client displays each member's avatar and name beside an individual background, border and rounded message bubble, with corresponding dark-theme styling. Historical root responses retain their original attribution.

Ordinary group sends use `queue`: save and acknowledge the message without cancelling active members or their approvals. A busy member answers queued questions after its current execution and awaited results finish; no second model runs concurrently in that member's Session. Owner pauses, budget pauses and unconfirmed outcomes stay paused when a queued message arrives. Continue resumes a permitted paused run with its saved deliveries; a stopped or completed group starts a new run on its next ordinary message. Only the explicit Interrupt and adjust action or Host `mode: 'steer'` replaces the run: admit attachments and save the new instruction and run together, then cancel and drain the captured old execution chain and its approvals before starting the new run. Rapid sends serialize within that group without delaying another group. Saved messages, completed receipts and files remain; already started external effects cannot be rolled back. Identical request retries reuse the saved input without another interruption. Private conversation transports are unchanged. If saving fails before acceptance, the old run remains; if acceptance or cancellation cannot be confirmed, the group reports failure and stops dependent execution for inspection.

The composer dock displays actual running members through their avatar, name and individual working, approval or awaiting-answer phase. Multiple members rotate every four seconds; hovering, keyboard focus or a hidden document pauses rotation, and reduced motion lists them statically. Rotation does not announce each change to screen readers. A tiny neutral diamond marks the current saved group manager beside member messages, handoffs, task identities, approvals and group settings, matching Bot IDs while retaining historical sender names. Private and composite group avatars have no manager marker. The ten Bean Bot avatars reuse seven hover motions on hover-capable pointers; reduced motion disables them. ## Persistence and recovery

The new `katcats_team` storage domain has version 1 and no migration from another product. A single atomic global record holds groups, members and interrupted-operation state. A member appears only after its private Session is durable. `pendingRename` holds the complete target for title or model settings until the Session flush and member record both commit. Refused model input with no Session change clears that target. An accepted or uncertain model switch retains its target on failure and reports incomplete settings; a later snapshot or restart retries it without reporting success early. Pure title failures restore the old title when possible. Unknown versions and invalid identities fail instead of resetting data.

Member identity is independent of its private Session ID. The plugin uses public Session APIs and scoped prompt sections; it does not modify the agent loop. Fixture tests use temporary directories and synthetic model adapters, separately from development user data.

## Model Experience

### Member identity

#### What the model sees

The member's saved name and role replace the product persona section for that member's private Agent. Private and group member prompts identify 瑞华云财务共享团队 and direct future introductions to use it even when earlier conversation contains an old product name. Saved roles and historical replies are not rewritten. With no role, the prompt uses this literal:

##### General-assistant role

```markdown
You are a general assistant. Work with the user to establish your role.
```

#### Token effect

The name and current role contribute to each assembled system prompt. Editing a role changes the next assembly; it does not rewrite a request already in progress. The existing system-message events record the effective text.

#### KV Cache effect

Unchanged member identity preserves this prompt section. Editing the name or role replaces its text and may invalidate the affected prompt prefix.

### Model selection

#### What the model sees

Fixed-model changes use the existing [Agent model-selection mechanism](../../core/agent/README.md): the next admitted request records its model-switch notice and route in the Session log. They do not rewrite earlier requests or messages.

#### Token effect

A route change adds the existing model-switch notice to the next admitted request. Choosing a model does not itself run a model request.

#### KV Cache effect

Choosing another model may move the request to a different provider cache; provider caching and eviction remain outside this package.

### Conversational tools

#### What the model sees

Member-tool schemas enter only the owning Agent's requests. Their calls and structured results use the existing tool log; role changes enter the next assembled identity section. Tool guidance requires an explicit lasting-identity request and reserves ordinary tasks for the current conversation.

#### Token effect

Tool schemas, results and saved roles consume request tokens; the main and ordinary members have different tool sets.

#### KV Cache effect

The owning member retains its stable tool definitions; changing a saved role changes the identity prefix on the next assembly.

### Group chat

#### What the model sees

Member requests add the roster, saved roles, responsible-member and review guidance, and selected public group messages. The current task retains its original content; saved result metadata references one copy of each reply. History queries return original text, images and attachments through logged tool results. Delivery guidance requires usable text or actual `present` registration; important work also requires approval of that exact candidate. Delegation results contain confirmed member outcomes rather than queue acknowledgements. Prompts, versioned context manifests, review evidence and messages use normal Session logging. Published output comes from the actual member Session with its captured identity; the transcript has no model persona or requests.

#### Token effect

Only dispatched members make model requests; an irrelevant member is not called merely to decide whether to pass. Persisted message identities avoid reappending already supplied group history, while distinct messages remain distinct. Existing executor history, summaries, tool definitions, history queries and independent review still consume tokens. Deterministic fixtures verify routing and duplication, not real-model quality or billed savings. Those claims require same-model, same-task comparisons using actual cached input, uncached input, output, cost, latency and delivery checks.

#### KV Cache effect

Changing the roster or guidance can invalidate the affected prompt prefix; unchanged member identities preserve their own prefix within each isolated Session.

### Scoped memories

#### What the model sees

Scoped memory tools and serialized entries use the public tool and system-prompt mechanisms and normal request logs. Saved facts are untrusted data, grant no permissions, and cannot select another Bot's scope. The prompt reports omitted entries, and recall can retrieve saved facts excluded from its bounded context.

#### Token effect

Memory schemas, selected entries and recall results consume tokens within the configured limits. Deleting a fact does not erase earlier requests that already recorded it.

#### KV Cache effect

Changing visible memory replaces its prompt section and may invalidate the affected prefix; unchanged entries keep stable serialized content.

## Known Limitations and Deferred Work

- Dynamic model following covers product prompt admission and owned group dispatch or continuation, without changing unrelated direct SDK, ACP or scheduled followups.
- Group Stop waits for any model-selection metadata lookup already admitted through the public Session API to settle; that API does not accept cancellation. No member model request is dispatched after the captured run has stopped.
- Group receipts publish final member text, Markdown file links, registered final files and successful visualization cards from the exact completed executor turn. Updated charts use the latest saved result per path. When independent review is required, the visualization must match the approved file bytes. Other tool-result cards stay in the executor Session. A successful file registration followed by an error or interruption without a completed closing reply stays saved in that Session but has no final group card; inspect the saved result before retrying.
- Recall uses case-insensitive substring matching without embeddings. Credential-pattern rejection is heuristic: it neither echoes nor saves recognizable secrets in memory but cannot erase input already authored in a message or tool call. Deletion preserves earlier shared copies and request logs.
- Automation lists associate existing Schedule records with Bots and groups. Scheduled group execution is not connected: the Schedule service delivers directly to the original Session, while group members accept only product-owned group work. Listing a task or retaining a delivery receipt does not confirm that the task ran or completed. Private handoffs, group schedule delivery and broader capability parity remain in the development plan.
- Settings display the creation-owned work directory. Changing an existing member's directory requires the later file and permission lifecycle work.
